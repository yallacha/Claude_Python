| 활동 | 결과 | 근거 |

## 2. 요구사항 품질 점검

| 기준 | 결과 | 비고 |
|---|---|---|
| 단일성 | 충족 | SWR-013은 OEM-SR-003 한 건을 그대로 따라 검증·freshness를 함께 다룬다. 검증 기준을 ①~⑤로 나눠 개별 검증 가능 |
| 검증 가능성 | 충족 | "빠르게", "적절히" 같은 표현 없음. 시간·값·필드를 수치로 명시 |
| 모호성 | 충족 | 경계값 포함 여부 명시(3.0 이상, 200 ms 초과, 10.0 s 이하) |
| 일관성 | 충족 | 규칙 충돌은 SWR-022로 해소. 이유 코드 단일화 규칙 명시 |
| 실현 가능성 | 충족 | Python 3.12 PC/SIL에서 구현 가능. HIL·실차 의존 없음 |
| 추적성 | 충족 | 모든 SWR에 상위 OEM 요구 |

## 3. 발견 사항

| ID | 위치 | 내용 | 처리 |
|---|---|---|---|
| REV-F-01 | OEM 5장 전체 | 규칙이 동시에 성립할 때의 우선순위가 없다(예: 주행 자동잠금과 성인 탑승 해제, ISOFIX 잠금과 화재 해제) | D-01 → SWR-022 |
| REV-F-02 | OEM-FR-003 / OEM-SR-002 | QM 요구(override)가 ASIL B 요구(접근위험 해제 억제)를 풀 수 있는 구조 | D-02: override는 기록만, 잠금 유지 → SWR-006 |
| REV-F-03 | OEM-IF-001 `gear` | 입력 계약에는 있으나 판정에 쓰는 OEM 요구가 없다 | 유효성 검증만 수행(SWIF 1장). OEM 확인 질의 Q-03 |
| REV-F-04 | OEM-IF-001 / OEM-IF-004 | 시각 필드 이름이 `source_timestamp_s`와 `VehicleSnapshot.timestamp_s`로 다르다 | D-11: 같은 필드로 해석 → SWIF 1·2장 |
| REV-F-05 | OEM-SR-001 | "이후 입력 주기에도 유지된다"의 유지 기간이 없다 | D-12: 시동 꺼짐까지 유지 → SWR-007 |
| REV-F-06 | OEM-SR-003 | 형식·범위 오류 입력을 "정의된 방식"으로 처리하라고만 되어 있다 | D-13: 거절 후 출력 유지, INVALID → SWR-013 |
| REV-F-07 | OEM-FR-007 | "초기 해제 상태"의 기동 시 정의가 없다 | D-14: 기동 시 RELEASE, OFF, NO_DATA → SWR-024 |
| REV-F-08 | OEM-FR-005 | 화재·과온·성인 탑승이 동시에 들어올 때 이유 코드가 정해지지 않았다 | D-15: 화재 > 과온 > 성인 → SWR-017 |
| REV-F-09 | OEM-SR-001, OEM-SR-003 | "평가주기"의 주기가 없어 300 ms, 100 ms 판정 기준이 없다 | D-03: 50 ms → SWR-023 |
| REV-F-10 | OEM 9장 | 추적 계획에 SWR-019가 없다 | D-08: 결번 처리 |
| REV-F-11 | OEM-SR-003 | DEGRADED 상태의 출력과 "필수 입력"이 없다 | D-04 → SWR-013 |
| REV-F-12 | OEM-SR-001 / 9장 | 추적 계획에 PENDING 처리가 있으나 OEM 요구에 PENDING 동작이 없다 | D-05 → SWR-008 |
| REV-F-13 | OEM-NFR-002 | "허용 필드" 목록이 없다 | D-06 → SWR-011, SWIF 6장 |
| REV-F-14 | OEM 4장 / OEM-FR-001 | 4장은 "모바일 앱, 음성으로 차일드락 제어가 가능하다는 주장"을 금지하지만 FR-001은 voice·mobile_app 경로를 요구한다 | 모순 아님: 4장 금지는 Tesla 공개 기능을 근거로 한 주장에 대한 것이고, FR-001은 가상 OEM-A 자체 요구. 변경 없음 |

## 5. 결론

SWE.1 산출물은 G1(BL-SWR-1.0) 조건을 갖췄고, 2026-11-26 사용자(OEM-A 역할)가 승인했다. 4장 질의는 OEM 답변 전까지 공급자 가정으로 유지한다.
