# CR 변경 요청

승인된 베이스라인(BL-SWR-1.0, BL-SWA-1.0)을 바꾸는 요청을 기록한다. 승인 전에는 변경이 확정되지 않는다.

## CR-01 SWR-004 운전자 명령 거절 시 이유 코드 범위

| 항목 | 내용 |
|---|---|
| 상태 | 승인 (사용자, 2026-11-26, PR #6) |
| 발견 | 상세 설계(SWD 5.3 명령 효과 처리) 중, 2026-11-26 |
| 대상 | BL-SWR-1.0 SWR-004 |
| 영향 SWR | SWR-004 (변경), SWR-007·SWR-013·SWR-021 (변경 없음, 충돌 해소) |

**문제**

SWR-004는 "1~7순위 규칙이 적용되는 출력에 명령이 오면 `reason_code`를 접근위험이면 `approach_risk_<side>`, 그 밖에는 `driver_rejected`로 한다"고 요구한다. 그런데 같은 상황에서

- SWR-021은 센서 고장 중 `reason_code=sensor_fault`를,
- SWR-013 ③은 freshness 상실 중 `input_stale`(DEGRADED)을,
- SWR-007은 충돌 확정 중 `reason_code=crash_confirmed`를

요구한다. 센서 고장 중에 운전자 명령이 들어오면 두 요구가 서로 다른 값을 요구해 동시에 만족할 수 없다.

**변경 내용**

SWR-004의 이유 코드 규칙을 아래처럼 바꾼다.

| 막은 규칙 | 변경 전 | 변경 후 |
|---|---|---|
| 1순위 충돌, 2순위 센서 고장·freshness 상실 | `driver_rejected` | 그 규칙의 이유 코드 유지(`crash_confirmed`, `sensor_fault`, `input_stale`) |
| 3순위 접근위험 | `approach_risk_<side>` | 변경 없음 |
| 4~7순위 | `driver_rejected` | 변경 없음 |

**근거**: 1~2순위는 시스템 상태(긴급 해제, 고장, 입력 상실)를 알리는 이유 코드라 운전자 명령보다 표시 가치가 크다. OEM 수용기준(OEM-SR-004 "FAULT 상태와 경고코드 제공")과도 맞다.

**영향 분석**

| 산출물 | 영향 |
|---|---|
| SWR-004 요구사항·검증 기준 | 문구 변경. 검증 기준 ①~⑤는 모두 4~7순위 사례라 변경 없음. 1~2순위 사례 ⑥ 추가 |
| SWA | 없음 |
| SWD | 5.3 명령 효과 처리 표가 변경 후 규칙을 반영 |
| 추적성 | 없음 |
