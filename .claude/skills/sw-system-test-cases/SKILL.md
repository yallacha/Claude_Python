# SW 시스템 테스트 케이스 생성

테스트 베이시스(SW 요구사항)를 받아, 심사(A-SPICE assessment)와 안전 감사(ISO 26262 confirmation)에서 그대로 증적으로 쓸 수 있는 테스트 케이스 엑셀을 만든다.

좋은 결과물의 기준은 "케이스 수"가 아니다. 다음 세 가지를 **검증 가능한 형태로** 보여 주는 것이다.

1. 모든 요구사항이 하나 이상의 실행 가능한 테스트 케이스로 검증된다 (추적성·커버리지 100%).
2. 각 테스트 케이스가 왜 존재하는지, 어떤 기법으로 어떤 값이 도출됐는지 설명된다.
3. 쓸모없는 케이스가 없다. 모든 케이스는 다른 케이스가 잡지 못하는 결함을 잡을 수 있다.

## 사용하는 파일

| 파일 | 언제 읽나 |
|---|---|
| `references/standards.md` | 처음 한 번. A-SPICE SWE.6과 ISO 26262-6 요건을 이 스킬의 산출물 어디에서 만족하는지 정리 |
| `references/techniques.md` | 테스트 설계(3단계) 전에. 동치 분할·경계값·페어와이즈·WoW 적용 규칙과 예시 |
| `references/data-format.md` | 엑셀을 만들기 전에. `build_workbook.py`에 넘기는 JSON 형식과 양식(template) 매핑 |
| `scripts/run_pict.py` | 페어와이즈 조합 도출. PICT가 없으면 GitHub 공식 릴리스에서 받아 해시를 확인한 뒤 실행 |
| `scripts/build_workbook.py` | JSON → 엑셀. 저장 전에 추적성·커버리지·필수 항목을 검사하고, 문제가 있으면 엑셀을 만들지 않고 실패 |

Python은 `python`이 PATH에 없으면 `%LOCALAPPDATA%\Programs\Python\Python312\python.exe`를 쓴다. `openpyxl`이 필요하다.

## 작업 순서

### 1단계. 입력 확인

**테스트 베이시스가 없으면 작업을 시작하지 않고 사용자에게 요청한다.** 제품 이름, 기능 한 줄 설명, "일반적인 도어 잠금 기능" 같은 말만 있는 경우도 베이시스가 없는 것으로 본다. 이때 요구사항을 추측해서 만들거나, 업계 상식·유사 제품·이전 대화를 근거로 요구사항을 채워 넣지 않는다. 추측한 베이시스로 만든 케이스는 추적성과 커버리지 숫자가 모두 맞아 보이지만, 실제 요구사항을 하나도 검증하지 못하기 때문이다. 요청할 때는 무엇이 필요한지 구체적으로 말한다:

- 요구사항 문서(SRS, SW 요구사항 엑셀 등) — 요구사항 ID, 요구사항 본문, 가능하면 ASIL
- 입력·출력 신호 정의(범위, 단위, 분해능). 경계값 계산에 필요하다
- 회사 테스트 케이스 양식(있으면)

베이시스가 일부만 있을 때도 같다.
- 받은 요구사항만 테스트 대상으로 삼는다. 빠져 보이는 기능이 있어도 요구사항을 새로 만들지 않고, "이 기능의 요구사항이 빠진 것 같다"고 질문한다.
- 요구사항이 참조하는 문서(신호 사양, 파라미터 표, 상위 요구사항 등)가 없어서 값이나 기대 결과를 정할 수 없으면, 그 문서를 요청하고 해당 요구사항은 `open_issues`로 남긴다. 값을 짐작해서 채우지 않는다.
- 사용자가 "그냥 예시로 만들어 줘"처럼 가상의 베이시스를 명시적으로 원하면 만들 수 있다. 이 경우 요구사항 ID 앞에 `SAMPLE-`을 붙이고, 산출물 제목과 보고에 "실제 베이시스가 아닌 예시"라고 밝힌다.

베이시스를 받으면:

- **테스트 베이시스**: 요구사항 문서(엑셀, 워드, PDF, 텍스트 등). 요구사항마다 ID가 있어야 추적성이 성립한다. ID가 없으면 `REQ-001`처럼 부여하고, 부여한 ID와 원문 위치의 대응표를 사용자에게 보여 준다. ID 부여는 번호만 붙이는 것이고, 요구사항 내용은 원문 그대로 쓴다.
- **테스트 케이스 양식**: 사용자가 양식(엑셀 파일 또는 열 목록)을 주면 그 양식을 따른다. 없으면 기본 양식을 쓴다. 기본 양식에는 다음 7개 항목이 반드시 들어간다: 테스트 케이스 ID, 테스트 베이시스 ID, 테스트 목적, 입력 값, 절차, 예상 출력 값, 사용한 테스트 기법. 실행 가능성을 위해 사전 조건, 합격 기준, 테스트 환경, ASIL, 우선순위, 구분(요구/[제안])도 함께 넣는다.
- 사용자가 직접 테스트 케이스나 시나리오를 함께 줬다면 그것은 "사용자 케이스"다. 그대로 포함하고 [제안] 표시를 하지 않는다.

### 2단계. 요구사항 분석

요구사항을 하나씩 읽고 다음을 정리한다.

- **분류**: 기능(functional) / 비기능(non-functional: 성능·타이밍, 자원 사용량, 신뢰성, 안전 메커니즘의 반응 시간, 보안, 시동·종료 시간 등). 이 분류가 엑셀 시트를 가른다.
- **입력·출력과 그 정의역**: 각 입력의 범위, 단위, 분해능(LSB), 이산 값 목록, 출력이 관측되는 지점(CAN 신호, 출력 핀, 진단 응답, 로그 등).
- **테스트 가능성**: 합격/불합격을 객관적으로 판정할 수 없는 요구사항(예: "빠르게 반응해야 한다", 범위 밖 입력에 대한 동작이 정의되지 않음)은 **케이스를 지어내지 않는다**. `open_issues`에 질문으로 남기고 사용자에게 보고한다. 기대 결과를 추측해서 채우면 실행은 되지만 틀린 판정을 낳는 케이스가 되고, 이것이 가장 해로운 쓰레기 케이스다.

모호한 요구사항이 몇 개 있다고 작업을 멈추지 말고, 나머지는 끝까지 설계한 뒤 질문을 한꺼번에 보고한다.

### 3단계. 테스트 설계

`references/techniques.md`를 읽고 요구사항마다 적용한다.

1. **동치 분할 (필수)**: 입력이 있는 모든 요구사항에 유효/무효 클래스를 정의한다.
2. **경계값 분석 (필수)**: 순서가 있는 범위(수치, 시간, 길이, 개수)가 있는 모든 요구사항에 경계값을 도출한다. 경계값은 분해능 단위로 계산한다.
3. **페어와이즈 (가능한 경우)**: 서로 상호작용하는 독립 파라미터가 3개 이상이고 전체 조합이 실행하기에 너무 많을 때 적용한다. 조합은 **반드시 PICT로** 도출한다. 손으로 만든 "페어와이즈 표"는 쓰지 않는다. 손으로 만들면 쌍 누락을 검증할 수 없기 때문이다.
   ```
   python scripts/run_pict.py <model.txt> --out <결과.tsv> [--order 2]
   ```
   모델 파일과 결과 파일은 산출물 폴더에 남겨 증적으로 쓴다. 적용하지 않은 요구사항은 이유(파라미터 2개 이하, 이산 조합 없음 등)를 설계 시트에 남긴다.
4. **엣지 케이스와 WoW (필수 검토)**: 단일 경계가 아닌 극단 상황(동시 다발 입력, 최대 부하, 전원·타이밍 극단, 고장 중첩)을 찾고, 여러 변수를 동시에 최악 값으로 둔 WoW 케이스를 만든다. 테스트 기법 열에 `WoW(Worst-of-Worst)`라고 명시하고, 어떤 변수를 어떤 최악 값으로 묶었는지 테스트 목적에 쓴다.
5. ISO 26262-6이 요구하는 **요구사항 기반 테스트**와, 안전 메커니즘이 있는 요구사항의 **고장 주입 테스트**를 빠뜨리지 않는다. 오류 추정(error guessing)도 기법으로 쓸 수 있다.

설계 결과(클래스·경계값·조합)는 JSON의 `design` 항목에 기록하고, 각 항목이 어느 테스트 케이스로 덮이는지(`covered_by`) 적는다. 이것이 "동치 클래스·경계값 커버리지 100%"의 증거다.

### 4단계. 테스트 케이스 작성

각 케이스는 테스트 엔지니어가 다른 문서를 보지 않고 바로 실행할 수 있어야 한다.

- **입력 값**은 구체적인 값과 단위로 쓴다. "유효한 값", "범위 밖 값"은 안 된다. `차속 = 120.0 km/h (상한 경계)`처럼 쓴다.
- **절차**는 번호를 붙인 단계로, 관측 시점까지 포함한다.
- **예상 출력 값**은 요구사항 원문에서 도출하고, 판정 가능한 값·허용 오차·시간 한계를 쓴다. 요구사항에 근거가 없는 기대값은 쓰지 않는다.
- **테스트 환경**은 실제로 그 입력을 만들 수 있는 환경(SIL, HIL, 실차, 디버거 고장 주입 등)으로 적는다. 정의된 환경에서 만들 수 없는 입력이면 그 케이스는 만들지 않는다.

**쓰레기 케이스 금지 규칙**: 다음에 해당하면 만들지 않거나 합친다.

- 다른 케이스와 같은 클래스·같은 경계·같은 조합을 반복하는 케이스
- 요구사항 문장을 그대로 옮기고 구체 값이 없는 케이스
- 판정 기준이 없거나 "정상 동작할 것" 같은 기대 결과를 가진 케이스
- 커버리지 숫자를 맞추려고 요구사항 하나에 기계적으로 붙인 케이스

반대로, 유효 클래스는 한 케이스에 여러 개를 함께 넣어도 되지만 **무효 클래스는 한 케이스에 하나만** 넣는다. 무효 입력이 두 개면 어느 쪽 때문에 거부됐는지 알 수 없기 때문이다.

**[제안] 표시**: 테스트 베이시스를 검증하는 데 필요한 케이스는 일반 케이스다. 베이시스가 직접 요구하지 않지만 Claude가 위험하다고 판단해 추가하는 케이스(예: 요구사항에 없는 동시 입력, 명세되지 않은 강건성 확인)는 `proposed: true`로 두고, 테스트 목적 앞에 `[제안]`을 붙인다. 이런 케이스도 가장 가까운 요구사항 ID에 추적시키되, 커버리지 계산에는 넣지 않는다. 커버리지를 [제안] 케이스로 채우면 베이시스 검증을 과대평가하게 되기 때문이다.

### 5단계. 추적성·커버리지 검증과 엑셀 생성

`references/data-format.md` 형식으로 JSON을 쓰고 실행한다.

```
python scripts/build_workbook.py <testcases.json> --out <결과.xlsx> [--template <양식.xlsx>]
```

스크립트는 엑셀을 쓰기 전에 다음을 검사한다. 하나라도 실패하면 엑셀을 만들지 않고 오류를 출력한다. 오류를 고쳐 다시 실행한다. 검사를 끄거나 우회하지 않는다.

- 모든 테스트 케이스가 존재하는 베이시스 ID를 참조하는지 (역방향 추적성)
- 테스트 가능한 모든 요구사항이 [제안]이 아닌 케이스로 1개 이상 덮이는지 (순방향 추적성, 베이시스 커버리지)
- 모든 `design` 항목(동치 클래스, 경계값, PICT 조합)이 실제 케이스로 덮이는지
- 필수 항목이 비어 있지 않은지, ID 중복이 없는지, 기법이 하나 이상 있는지
- 입력이 있는 요구사항에 동치 분할과 경계값 분석이 적용됐는지

만들어지는 시트: `기능 테스트`, `비기능 테스트`, `테스트 설계`(EP/BVA/페어와이즈/WoW 도출 근거), `추적성 매트릭스`(요구사항 ↔ 테스트 케이스 양방향), `커버리지 요약`, `미결 사항`.

### 6단계. 보고

엑셀 경로와 함께 다음을 짧게 보고한다.

- 요구사항 수(기능/비기능), 케이스 수(일반/[제안]), 베이시스 커버리지
- 페어와이즈를 적용한 요구사항과 PICT 결과 파일, 적용하지 않은 이유
- WoW 케이스 목록
- 테스트할 수 없어 케이스를 만들지 않은 요구사항과 질문 (`미결 사항`). 이런 요구사항이 있으면 커버리지를 100%라고 말하지 말고, "테스트 가능한 요구사항 기준 100%, 미결 N건"처럼 정확히 말한다.
