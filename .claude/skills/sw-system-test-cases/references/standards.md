# 표준 요건과 산출물 대응

이 스킬의 산출물이 각 요건을 어디에서 만족하는지 정리한다. 심사·감사에서 "어디에 있나"라는 질문에 시트 이름으로 답할 수 있게 하는 것이 목적이다.

조항·표 번호는 판(edition)에 따라 다르므로, 사용자가 특정 판을 쓰면 그 판의 번호를 따른다. 아래는 A-SPICE 3.1 / 4.0, ISO 26262:2018 기준이다.

## A-SPICE SWE.6

3.1에서는 "Software Qualification Test", 4.0에서는 "Software Verification"이다. 사용자가 판을 말하지 않으면 두 판 모두를 만족하도록 만든다.

| 요건 (3.1 BP / 4.0 BP) | 이 스킬에서 만족하는 곳 |
|---|---|
| 테스트 전략 (3.1 BP1) | 범위 밖. 사용자가 전략 문서를 주면 그 기법·환경·합격 기준을 따른다. 없으면 이 스킬의 기법 규칙(`techniques.md`)을 기본 전략으로 보고한다 |
| 테스트 명세 / 검증 수단 명세: 테스트 케이스, 기법, 합격 기준, 환경 (3.1 BP2, 4.0 BP1) | `기능 테스트`·`비기능 테스트` 시트(입력, 절차, 예상 출력, 합격 기준, 환경), `테스트 설계` 시트(도출 근거) |
| 테스트 케이스 선정 (3.1 BP3, 4.0 BP2) | 우선순위 열, 쓰레기 케이스 금지 규칙, [제안] 구분 |
| 양방향 추적성 (3.1 BP5, 4.0 BP4) | `추적성 매트릭스` 시트: 요구사항 → 케이스, 케이스 → 요구사항. `build_workbook.py`가 누락을 검사 |
| 일관성 (3.1 BP6, 4.0 BP4) | 예상 출력 값은 요구사항 원문에서만 도출. 근거 없는 기대값 금지. 불명확하면 `미결 사항` |
| 테스트 실행·결과 요약 (3.1 BP4/BP7, 4.0 BP3/BP5) | 범위 밖(실행 단계). 시트에 실행 결과·판정 열을 비워 두어 실행 기록에 그대로 쓸 수 있게 한다 |

## ISO 26262-6 제11절: 임베디드 소프트웨어 테스트

| 요건 | 이 스킬에서 만족하는 곳 |
|---|---|
| 테스트 환경 (HIL, ECU 네트워크, 차량 등) | 각 케이스의 `테스트 환경` 열. 입력을 실제로 만들 수 있는 환경만 적는다 |
| 검증 방법: 요구사항 기반 테스트 | 모든 일반 케이스. 베이시스 ID로 추적 |
| 검증 방법: 고장 주입 테스트 | 안전 메커니즘·오류 처리 요구사항마다 고장 주입 케이스(기법 열에 `고장 주입`) |
| 테스트 케이스 도출 방법: 요구사항 분석 | 2단계 분석 결과와 `테스트 설계` 시트 |
| 테스트 케이스 도출 방법: 동치 클래스 생성·분석 | `테스트 설계` 시트의 EP 항목 |
| 테스트 케이스 도출 방법: 경계값 분석 | `테스트 설계` 시트의 BVA 항목 |
| 테스트 케이스 도출 방법: 지식·경험 기반 오류 추정 | 엣지 케이스·WoW 케이스, 기법 열에 `오류 추정` |
| 요구사항 커버리지 | `커버리지 요약` 시트 |
| ASIL에 따른 방법 강도 | 요구사항의 ASIL을 열로 남긴다. ASIL C/D 요구사항은 3값 경계값과 고장 주입을 기본으로 한다(`techniques.md`) |

ISO 26262 Part 6의 단위(unit) 테스트와 통합 테스트(제9절, 제10절)는 이 스킬의 대상이 아니다. 사용자가 SW 단위 테스트 케이스를 요청하면 구조 커버리지(문장/분기/MC/DC) 같은 다른 요건이 붙으므로, 그 사실을 알리고 범위를 확인한다.
