4. 엣지 케이스와 WoW (Worst-of-Worst)

## 1. 동치 분할 (EP) — 필수

입력(또는 상태, 이벤트)이 있는 모든 요구사항에 적용한다.

- 요구사항이 같은 방식으로 처리한다고 정의한 값의 집합이 하나의 클래스다. 클래스는 요구사항 원문을 근거로 나눈다. 구현을 추측해서 나누지 않는다.
- 유효 클래스와 무효 클래스를 모두 정의한다. 무효 클래스의 기대 동작(거부, 기본값, DTC 저장 등)이 요구사항에 없으면 케이스를 만들지 않고 `open_issues`에 질문한다.
- 클래스 ID는 `EP-<요구사항ID>-V1`, `EP-<요구사항ID>-I1`처럼 붙인다.
- 각 클래스에서 대표값 하나를 고른다. 경계와 겹치지 않는 중간 값이 좋다. 경계는 BVA가 따로 다룬다.
- 유효 클래스 여러 개는 한 케이스에 함께 넣을 수 있다. 무효 클래스는 케이스당 하나만 넣는다.

## 2. 경계값 분석 (BVA) — 필수

순서가 있는 범위(수치, 시간, 길이, 개수, 주기)가 있는 모든 요구사항에 적용한다.

- 경계값은 요구사항이 정의한 **분해능(LSB, 신호 스케일)** 단위로 계산한다. 분해능이 없으면 신호 정의(DBC 등)에서 찾고, 그래도 없으면 가정한 분해능을 `open_issues`에 남긴다.
- 기본은 2값 경계: 경계값과 바로 바깥 값. 예: 범위 0~120 km/h, 분해능 0.1 → 0.0, -0.1, 120.0, 120.1
- ASIL C/D 요구사항, 그리고 비교 연산자(`>` / `>=`)가 헷갈리기 쉬운 임계값은 3값 경계: 안쪽 값, 경계값, 바깥 값. 예: 119.9, 120.0, 120.1
- 시간 경계(타임아웃, 디바운스)는 측정 오차를 고려해 허용 오차를 예상 출력에 적는다. 예: "100 ms ± 5 ms 안에 출력"
- 물리적으로 만들 수 없는 경계 바깥 값(예: 신호 범위 자체가 0부터라 -0.1을 보낼 수 없음)은 그 사실을 설계 시트에 남기고 케이스를 만들지 않는다. "실행할 수 없는 케이스"가 되기 때문이다. 다만 원시 신호값(raw)으로 범위 밖을 보낼 수 있다면 그 방법을 절차에 쓴다.
- 경계값 ID는 `BV-<요구사항ID>-01`처럼 붙인다.

## 3. 페어와이즈 (PICT) — 가능한 경우

### 적용 판단
- 적용한다: 서로 상호작용할 수 있는 독립 파라미터가 **3개 이상**이고, 각 파라미터 값이 이산적(또는 EP로 이산화 가능)이며, 전체 조합이 실행하기에 많을 때.
- 적용하지 않는다: 파라미터가 2개 이하(전체 조합을 다 하면 됨), 파라미터 사이에 상호작용이 없음이 요구사항상 분명함, 전체 조합이 이미 적음. 적용하지 않은 이유를 설계 시트에 남긴다.
- ASIL C/D이고 특정 3개 파라미터의 상호작용이 안전에 영향을 주면 `--order 3`을 고려한다.

### PICT 사용
- 도구: https://github.com/microsoft/pict (공식 릴리스 `pict.exe`). `scripts/run_pict.py`가 PATH, `%LOCALAPPDATA%\pict\pict.exe` 순서로 찾고, 없으면 공식 릴리스에서 받은 뒤 SHA-256을 확인한다.
- 파라미터 값에는 EP 클래스의 대표값과 필요한 경계값을 넣는다. 값 하나가 수십 개가 되지 않도록 클래스로 묶는다.
- 요구사항상 불가능한 조합은 반드시 제약 조건으로 제외한다. 제외하지 않으면 실행할 수 없는 케이스가 나온다.
- 꼭 포함해야 하는 조합(예: 고객 대표 구성)은 시드 파일(`--seed`)로 넣는다.
- 무효 값은 PICT 음수 접두사(`~`)로 표시하면 한 조합에 무효 값이 하나만 들어간다.

모델 예시 (`pict_model_REQ-012.txt`):
```
# REQ-012: 시동 모드 x 전원 전압 x 기어 x 도어 상태
모드:   정상, 절전, 진단
전압:   9.0, 13.5, 16.0, ~8.9
기어:   P, R, N, D
도어:   열림, 닫힘

IF [모드] = "진단" THEN [기어] = "P";
```

실행:
```
python scripts/run_pict.py pict_model_REQ-012.txt --out pict_result_REQ-012.tsv
```

결과에서 `~`가 붙은 값(예: `~8.9`)은 무효 값이다. 케이스에 옮길 때 `~`는 빼고 무효 클래스임을 테스트 목적에 적는다.

결과의 각 행이 테스트 케이스 하나가 된다. 행마다 기대 결과를 요구사항에서 도출하고, 기법 열에 `페어와이즈(PICT)`를 쓴다. 설계 시트의 `design` 항목에 `PW-<요구사항ID>-01` 같은 ID로 각 행을 기록하고 `covered_by`를 연결한다. PICT 결과 행을 임의로 빼거나 바꾸지 않는다. 바꿔야 한다면 모델(제약)을 고쳐서 다시 돌린다.

## 4. 엣지 케이스와 WoW (Worst-of-Worst)

### 엣지 케이스
단일 경계값으로는 드러나지 않는 극단 상황이다. 다음 관점으로 찾는다.

- 시간: 동시 도착 이벤트, 주기 경계에서의 입력 변화, 타임아웃 직전·직후의 복귀, 초기화 직후·종료 직전 입력
- 상태: 모드 전환 중 입력, 같은 요청 반복, 상태 머신의 거의 쓰이지 않는 전이
- 자원: 큐·버퍼 가득 참, 최대 메시지 길이, 최대 부하
- 전원·환경: 저전압·과전압 경계에서의 동작, 리셋 복귀
- 데이터: 0, 최대값, 부호 전환, 오버플로 직전 값, 체크섬·카운터 롤오버

### WoW (Worst-of-Worst)
여러 변수를 **동시에** 각각의 최악 값으로 두어, 개별 경계 테스트에서는 드러나지 않는 마진 부족을 찾는 기법이다.

1. 대상 요구사항의 출력(반응 시간, 정확도, 자원 사용량 등)을 나쁘게 만드는 변수를 고른다.
2. 각 변수의 최악 방향을 정한다(예: 전압 최저, CPU 부하 최대, 입력 변화율 최대, 동시 이벤트 최대).
3. 그 값들을 한 케이스에 동시에 건다. 단, **정의된 동작 조건 안**에서만 묶는다. 동작 조건 밖까지 묶으면 기대 결과가 정의되지 않아 판정할 수 없다.
4. 테스트 목적에 "WoW: 전압 9.0 V(최저) + CAN 부하 80%(최대) + 입력 변화 10 ms 주기(최단)"처럼 무엇을 묶었는지 쓰고, 기법 열에 `WoW(Worst-of-Worst)`를 쓴다.
5. 예상 출력은 요구사항의 한계값(예: "200 ms 이내")을 그대로 쓴다. WoW에서도 한계를 지켜야 한다는 것이 이 케이스의 판정 기준이다.

WoW는 특히 비기능 요구사항(타이밍, 자원, 반응 시간)과 안전 메커니즘에 효과가 크다. 요구사항이 WoW 조건을 직접 요구하지 않으면 그 케이스는 [제안]이다.

## 5. 고장 주입과 오류 추정

- 안전 메커니즘·오류 감지 요구사항(타임아웃 감지, CRC 오류, 범위 검사, 워치독 등)에는 그 고장을 실제로 일으키는 케이스를 만든다. 절차에 고장을 만드는 방법(메시지 중단, CRC 변조, 디버거로 메모리 변조 등)을 구체적으로 쓴다.
- 오류 추정은 경험상 결함이 잦은 곳(초기값, 단위 변환, 부호, 롤오버, 재진입)을 겨냥한다. 근거를 테스트 목적에 쓴다.

## 6. 기법 이름 표기

기법 열에는 아래 이름만 쓴다. 여러 개면 쉼표로 구분한다. `build_workbook.py`는 이 이름으로 EP/BVA 적용 여부를 검사한다.

- `요구사항 기반`
- `동치 분할`
- `경계값 분석`
- `페어와이즈(PICT)`
- `WoW(Worst-of-Worst)`
- `고장 주입`
- `오류 추정`
- `상태 전이`
- `결정 테이블`
